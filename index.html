Autonomous infrastructure optimization · Zebra Technologies

PBI Sentinel

PythonGCP Cloud RunDatabricksPostgreSQLMS Graph APIOptimization
Diagnosis
Analyzed production metadata and found the cluster was hitting a 234% concurrent load peak on P3 nodes, and that 27,000 report refreshes a month were running for reports nobody opened. The zombie reports were the evidence that the scheduling was unmanaged. They justified the work rather than being the fix.
Approach
Designed a greedy optimization algorithm using quadratic and exponential weighting to rank refresh jobs and redistribute them into optimal windows. The savings come from the redistribution, not from deleting anything.
Autonomy
Wrapped it in an agent on GCP Cloud Run reading Databricks Unity Catalog and PostgreSQL, which negotiates new refresh times directly with report owners over Microsoft Teams via the MS Graph API. It asks rather than reassigns, which is why people accepted it.
Result
Projected peak load held under 55% capacity, saving $11K/month.

Distributed logging · ECE 428 · MP1

Log Querier

GoRPCDistributed grep
Problem
Query log files scattered across a cluster from any single machine, without copying them all to one place first.
Approach
Every server holds a bidirectional RPC connection to every other. Connections form lazily: if a peer is not up yet the server keeps running and links when it appears, so the mesh tolerates nodes starting in any order. A query fans out from the local server, each remote runs grep against its own file, and results are aggregated on the caller.
Benchmark
Five trials across five pattern frequencies on four machines, against ~60 MB of generated logs at ~150,000 lines per file. Latency is dominated by transfer and scales with match count rather than file size. With count-only queries it flattens to ~100 ms across every pattern.
Why it is here
This became the instrumentation the next three projects were benchmarked and debugged with. It is the bottom of the stack.

Group membership · ECE 428 · MP2

Membership

GoGossipSWIMUDP
Problem
Every node needs an accurate view of who is alive, over lossy UDP, without the traffic growing out of control as the cluster does.
Approach
Built both protocols and measured them against each other. Gossip carries the full membership list in every heartbeat. Ping-ack sends a direct ping, falls back to indirect pings routed through peers, and carries only the five most recent events. Both run with and without a suspicion layer, where a node goes SUSPICIOUS before FAILED and can refute the claim by incrementing its incarnation number.
Tuning
Parameters were derived rather than guessed: a 3s detection and 6s cluster-wide dissemination requirement gives a protocol period of 0.1s, putting a full round trip through ten nodes at 1.9s.
Result
Gossip bandwidth climbs with cluster size because the payload is the membership list; ping-ack stays nearly flat, capped at five events per message. Gossip gains most from suspicion since it has no other defence against a dropped heartbeat. Ping-ack's indirect probes already provide that, so without suspicion ping-ack detects faster and false-positives less.
Why it is here
Both HyDFS and RainStorm run their failure detection on this layer rather than reimplementing it.

Distributed stream engine · ECE 428

RainStorm

GoGoroutinesRPCSchedulingFault tolerance
Problem
Run continuous stateful operators over a stream without losing records when a worker dies mid-flight.
Approach
A leader-worker model where the leader schedules by load against a synchronized availability map. Operators run over a worker pool with at-least-once delivery, and state is checkpointed through HyDFS underneath. Routing supports shuffle, broadcast and fields-grouping.
Fault tolerance
A ping/ack channel system monitors tasks in real time and restarts them on failure, with the leader reassigning work when a member drops out.
Benchmark
Measured head-to-head against Spark Streaming on two Kaggle datasets: 7M lines of US traffic accidents and 23M lines of listening history for 500K users. On grep-replace Spark ran 503 tuples/sec to RainStorm's 322; on aggregate-transform, 2812 to 1757.
Why it is slower
About 40%, and the cause is specific: every output tuple and every log entry is a separate HyDFS append, so a run produces millions of one-line files and millions of requests. The bottleneck is the storage layer beneath it, not the scheduler. Batching appends and combining file output is the fix, and knowing exactly where the cost sits was the point of measuring.

Fault-tolerant file system · ECE 428

HyDFS

GoRPCHTTPReplicationEventual consistency
Problem
Keep files available and eventually consistent across a cluster where nodes crash and rejoin without warning.
Approach
A hybrid architecture that separates control flow from data flow: metadata moves over RPC, bulk transfers over HTTP, so metadata operations are not stuck behind large file writes. Files are stored as independent blocks, one per append, which is what makes concurrent writers cheap. Failure detection is not reimplemented here: it runs on the gossip membership layer from MP2.
Consistency
Eventual consistency at a replication factor of log(N) ≈ 3, with a background merge every 3 seconds reconciling blocks after a partition and re-replicating automatically on rejoin.
Result
Re-replication completes in ~3.6–3.9s and stays flat from 200 KB to 1 MB files: the cost is detection and merge interval, not transfer.
What I would change
Merge time is flat at ~0.17s no matter how many concurrent appends run, because appends already write to every replica synchronously. Merge downloads nothing in the common case, so it is insurance against partitions rather than part of the write path. Useful to know, but it means the design pays for a reconciliation pass it rarely needs.

LLM Dev Assistant

PythonLangChainFAISSFastAPIAsyncIOAST
Problem
Naive RAG over source code chunks by line count, which splits functions in half and retrieves fragments that do not mean anything on their own.
Approach
Chunk by Abstract Syntax Tree instead: split on real functional boundaries like classes and methods, so every retrieved unit is something a model can reason about whole.
